## 1. 总体概述

### 1.1 背景与目标

**业务背景**

患者通过 FT-001 身份验证进入患者门户后，需要一个清晰、有序的「我的问诊记录」视图：以列表形式查看自己提交的全部历史问诊，快速区分「待回答 / 已回答」，并对已回答的问题展开查看医生回复与回复时间。该特性聚焦于**前端展示层**，复用 FT-001 提供的历史问诊查询接口与数据模型，不改变后端领域逻辑。

**目标**

- 以列表形式展示患者本人全部历史问诊，按提交时间倒序排列。
- 通过状态标签快速区分「待回答 / 已回答」。
- 对已回答记录支持展开查看医生回复内容与回复时间。
- 提供状态筛选、内容摘要折叠、客户端分页与空状态，保障列表在任意数据规模下的可读性与体验闭环。

### 1.2 核心概念

| 概念 | 定义 |
| ------ | ------ |
| 问诊记录 / 问题（Question） | 患者提交的疾病咨询记录，由 qa-service-question 管理 |
| 状态（QuestionStatus） | 取值 `pending`（待回答）/ `answered`（已回答），本期仅覆盖两种 |
| 患者门户（Patient Portal） | 患者通过 FT-001 验证后查看自身健康信息的入口（复用 Consultation.vue 区块） |
| 内容摘要 | 折叠态下对问题内容截断约 50 字并以省略号收尾的展示形式 |
| 内联手风琴展开 | 在列表项内部展开/收起，显示完整问题、医生回复与回复时间 |
| 状态筛选标签页 | 全部 / 待回答 / 已回答，纯前端按 `status` 过滤 |
| 客户端分页 / 加载更多 | 前端对列表数据切片，首屏轻量、按需追加，不侵入后端接口契约 |

### 1.3 变更范围

| 变更模块 | 变更类型 | 变更描述 |
| ---------- | :--------: | ---------- |
| qa-web（前端） | 新增/改造 | 新增/改造患者门户内的问诊记录列表组件：倒序列表、状态标签、内容摘要、内联手风琴展开、状态筛选标签页、空状态与客户端分页「加载更多」 |
| qa-service-question（后端） | 无变更 | 复用 FT-001 规划的 `GET /api/questions?patientId=`，不新增接口 |
| qa-service-user（后端） | 无变更 | 患者身份由 FT-001 提供，不新增逻辑 |

### 1.4 关键决策

| # | 决策点 | 决策结论 | 理由摘要 |
| --- | ------ | ---------- | ---------- |
| 1 | 数据来源 | 复用 FT-001 真实接口 `GET /api/questions?patientId=` | FT-001 已规划并定义该接口与字段，直接复用最自然、避免重复定义；FT-002 定位前端展示层 |
| 2 | 页面位置 | 嵌入患者门户区块（复用 `Consultation.vue` / 新建 `PatientPortal` 视图） | 贴合 FT-001 既定门户设计，复用现有结构与交互，减少新建路由成本 |
| 3 | 状态标签范围 | 仅「待回答 / 已回答」两种 | 用户需求明确只要求两种状态；「已关闭」非本期范围，留作后续演进 |
| 4 | 筛选能力 | 提供状态筛选标签页（全部 / 待回答 / 已回答） | 显著降低长列表查找成本，纯前端按 `status` 过滤、实现成本低 |
| 5 | 内容摘要与展开 | 截断约 50 字摘要 + 内联手风琴展开（完整问题 + 答案 + 回复时间） | 折叠态紧凑便于扫读，展开态提供完整上下文，符合门户轻交互预期 |
| 6 | 加载策略 | 客户端分页 /「加载更多」 | 首屏轻量且实现成本低（前端切片），不侵入 FT-001 已规划接口契约 |
| 7 | 空状态 | 友好空状态提示「暂无问诊记录」 | 首建档患者场景必然触发，是必要体验闭环，实现成本低 |

## 2. 使用场景

### 2.1 场景一：查看本人全部问诊记录

**角色**：已通过 FT-001 身份验证的患者

**前置条件**：
- 患者已完成 FT-001 身份验证并进入患者门户。
- FT-001 历史问诊接口 `GET /api/questions?patientId=` 可访问。

**操作步骤**：
1. 患者登录并进入患者门户的问诊记录区块。
2. 系统调用 FT-001 接口，按 `patientId` 拉取该患者的全部问诊记录。
3. 系统以提交时间倒序渲染列表，每条记录展示：咨询医生姓名、状态标签（待回答/已回答）、问题内容摘要、提交时间。

**预期结果**：患者看到本人全部历史问诊，按倒序排列；待回答与已回答状态一目了然。

---

### 2.2 场景二：按状态筛选问诊记录

**角色**：已通过 FT-001 身份验证的患者

**前置条件**：
- 问诊记录列表已加载，且同时含「待回答」与「已回答」记录。

**操作步骤**：
1. 患者点击筛选标签页「待回答」。
2. 系统按 `status` 过滤，仅展示 `pending` 状态的记录。
3. 患者切换「已回答」或「全部」标签页查看相应记录。

**预期结果**：列表即时过滤，患者快速定位目标状态记录（纯前端过滤，无需重新请求）。

---

### 2.3 场景三：展开已回答记录查看答案

**角色**：已通过 FT-001 身份验证的患者

**前置条件**：
- 列表中存在「已回答（answered）」记录。

**操作步骤**：
1. 患者点击某条已回答记录的展开区域（内联手风琴）。
2. 系统展开显示完整问题内容、医生回复内容、回复时间。

**预期结果**：患者获取完整问诊上下文；折叠态显示约 50 字摘要，展开态信息完整。

---

### 2.4 场景四：大量记录的加载更多

**角色**：已通过 FT-001 身份验证的患者

**前置条件**：
- 该患者的问诊记录较多，超过首屏展示条数。

**操作步骤**：
1. 系统首屏渲染前 N 条记录。
2. 患者滚动到底部点击「加载更多」。
3. 系统以客户端分页方式追加后续记录。

**预期结果**：首屏轻量，患者可平滑加载全部记录，且不依赖后端分页接口。

---

### 2.5 场景五：首次建档患者查看空状态

**角色**：通过 FT-001 首次建档、尚无任何问诊记录的患者

**前置条件**：
- 患者已建档，但问诊记录为空。

**操作步骤**：
1. 患者进入问诊记录区块。
2. 系统检测到记录为空。

**预期结果**：显示友好空状态提示「暂无问诊记录」，形成完整体验闭环，避免空白困惑。
