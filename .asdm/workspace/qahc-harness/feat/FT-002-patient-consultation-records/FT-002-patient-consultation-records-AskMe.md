# FT-002 患者问诊记录查看 — 需求访谈追问

> 本文档记录对 FT-002 患者问诊记录查看特性的逐问题追问，用于澄清需求模糊点后制定最终需求规格。

**创建日期**：2026-07-14
**负责人**：Ivy
**状态**：已完成

---

## 背景摘要

### 核心价值

患者通过 FT-001 身份验证进入患者门户后，需要一个清晰、有序的「我的问诊记录」视图：以列表形式查看自己提交的全部历史问诊，快速区分「待回答 / 已回答」，并对已回答的问题展开查看医生回复与回复时间。该特性聚焦于**前端展示层**，复用 FT-001 提供的历史问诊查询接口与数据模型，不改变后端领域逻辑。

### 变更范围

| 变更模块 | 变更内容 |
| ---------- | ---------- |
| qa-web（前端） | 新增/改造患者门户内的问诊记录列表组件：倒序列表、状态标签、内容摘要、内联手风琴展开、状态筛选标签页、空状态与客户端分页加载 |
| qa-service-question（后端） | 无新增（复用 FT-001 规划的 `GET /api/questions?patientId=`） |
| qa-service-user（后端） | 无新增（患者身份由 FT-001 提供） |

### 初始需求

> 患者在门户页查看自己的所有历史问诊记录，包括待回答和已回答的问题。患者门户页以列表形式展示该患者的所有问题，按提交时间倒序排列。每条记录展示：咨询医生姓名、状态标签（待回答/已回答）、问题内容摘要、提交时间。已回答的问题展开显示医生回复内容和回复时间。

## 决策点

### 决策点 1：数据来源

**问题**：FT-002 的问诊记录数据从何而来？

**背景**：
- FT-001 已在 PRD 5.3 规划 `GET /api/questions?patientId=`（qa-service-question 提供），返回字段含 `doctorName / question / status / submitTime / answer / answerTime`。
- 现有前端 `data/question-list.json` 为本地 mock，结构与接口字段一致。
- FT-001 当前状态为「设计中」，API 尚未落地。

**选项**：

| 选项 | 描述 | 优点 | 缺点 |
| ------ | ------ | ------ | ------ |
| A | 复用 FT-001 的真实接口 `GET /api/questions?patientId=` | 避免重复造轮子；与架构一致；数据可持久共享 | 依赖 FT-001 交付进度 |
| B | 基于前端现有 mock 实现，暂不依赖后端 | 可独立并行开发，不阻塞 | 与最终形态不一致，需二次改造 |
| C | 优先调用真实接口，失败回退 mock | 兼顾开发与最终态 | 需维护两套数据适配，复杂度高 |

**推荐**：✅ 选项 A — 复用 FT-001 真实接口

**确认理由**：
1. FT-001 已规划并定义该接口与字段，直接复用最自然、避免重复定义。
2. FT-002 定位为前端展示层，不应重新定义数据来源。

**状态**：✅ 已确认

---

### 决策点 2：页面位置

**问题**：问诊记录列表放在哪里？

**背景**：
- `web/qa-web/src/views/Consultation.vue` 已包含「患者门户 + 历史问诊」区块（FT-001 场景 2.3），目前为本地 mock。
- 路由目前无独立的患者历史路由。

**选项**：

| 选项 | 描述 | 优点 | 缺点 |
| ------ | ------ | ------ | ------ |
| A | 嵌入患者门户区块（复用 Consultation.vue 门户 / 新建 PatientPortal 视图） | 复用现有门户结构，符合 FT-001 场景 | 门户视图可能变重 |
| B | 新建独立路由页 `/patient/history` | 结构清晰、可独立访问 | 需新增路由与导航 |
| C | 弹窗 / 抽屉（Drawer）形式 | 不打断当前流程 | 不适合长列表浏览 |

**推荐**：✅ 选项 A — 嵌入患者门户区块

**确认理由**：
1. FT-001 已定义门户含历史问诊区，嵌入最贴合既定设计。
2. 复用现有 `Consultation.vue` 门户交互，减少新建路由成本。

**状态**：✅ 已确认

---

### 决策点 3：状态标签范围

**问题**：列表状态标签覆盖哪些？

**背景**：
- 数据模型 `QuestionStatus` 含 PENDING/ANSWERED/CLOSED（0/1/2）。
- FT-001 question 表 `status` 取值 `pending` / `answered`。
- 用户原始需求仅提及「待回答 / 已回答」。

**选项**：

| 选项 | 描述 | 优点 | 缺点 |
| ------ | ------ | ------ | ------ |
| A | 仅 待回答 / 已回答 两种 | 贴合当前需求，简单清晰 | 不覆盖已关闭态 |
| B | 待回答 / 已回答 / 已关闭 三种 | 完整覆盖数据模型 | 当前需求未要求，增加复杂度 |

**推荐**：✅ 选项 A — 仅 待回答 / 已回答

**确认理由**：
1. 用户需求明确只要求两种状态标签。
2. `已关闭` 非当前范围，可作为后续演进，不纳入本期。

**状态**：✅ 已确认

---

### 决策点 4：筛选能力

**问题**：是否需要按状态筛选？

**背景**：
- 列表可能同时含待回答与已回答记录，患者常需快速定位。

**选项**：

| 选项 | 描述 | 优点 | 缺点 |
| ------ | ------ | ------ | ------ |
| A | 提供状态筛选标签页（全部 / 待回答 / 已回答） | 提升查找效率 | 轻微 UI 成本 |
| B | 不筛选，直接展示全部 | 最简 | 查找不便 |

**推荐**：✅ 选项 A — 提供状态筛选标签页

**确认理由**：
1. 筛选显著降低长列表查找成本，体验更友好。
2. 实现成本低（纯前端按 `status` 过滤）。

**状态**：✅ 已确认

---

### 决策点 5：内容摘要与展开交互

**问题**：折叠态「问题内容摘要」如何呈现？展开后展示什么？

**背景**：
- 每条记录需展示问题内容摘要；已回答项需展开显示医生回复与回复时间。
- 问题内容可能较长（如 `question-list.json` 中多句描述）。

**选项**：

| 选项 | 描述 | 优点 | 缺点 |
| ------ | ------ | ------ | ------ |
| A | 摘要截断约 50 字 + 省略号；展开为内联手风琴，显示完整问题 + 医生回复 + 回复时间 | 列表紧凑，信息完整 | 需实现截断与展开逻辑 |
| B | 折叠即显示完整问题；仅已回答项可展开查看答案 | 实现简单 | 列表较长时不利于扫读 |
| C | 摘要截断约 50 字；展开仅在已回答时显示答案 | 折叠态一致 | 展开不显示完整问题，上下文缺失 |

**推荐**：✅ 选项 A — 截断摘要 + 内联手风琴展开

**确认理由**：
1. 折叠态紧凑便于扫读，展开态提供完整上下文（问题+答案+时间）。
2. 内联手风琴符合门户页轻交互预期。

**状态**：✅ 已确认

---

### 决策点 6：加载策略

**问题**：记录较多时如何加载？

**背景**：
- 当前 mock 数据量小（7 条），但生产环境可能累积大量记录。

**选项**：

| 选项 | 描述 | 优点 | 缺点 |
| ------ | ------ | ------ | ------ |
| A | 客户端分页 / “加载更多” | 首屏轻量，可平滑扩展 | 需客户端分页逻辑 |
| B | 一次性全部渲染 | 实现最简单 | 大数据量时性能差 |
| C | 后端分页接口 | 性能最佳 | 需扩展 FT-001 API，超出本期范围 |

**推荐**：✅ 选项 A — 客户端分页 / “加载更多”

**确认理由**：
1. 首屏轻量，且实现成本低（前端切片）。
2. 不侵入 FT-001 已规划的接口契约。

**状态**：✅ 已确认

---

### 决策点 7：空状态

**问题**：无问诊记录时如何展示？

**背景**：
- 新建档患者（FT-001 首次建档）可能尚无任何问诊记录。

**选项**：

| 选项 | 描述 | 优点 | 缺点 |
| ------ | ------ | ------ | ------ |
| A | 友好空状态提示「暂无问诊记录」 | 体验友好，避免空白困惑 | 需额外 UI |
| B | 不特殊处理（空白列表） | 最简 | 用户易困惑 |

**推荐**：✅ 选项 A — 友好空状态提示

**确认理由**：
1. 首建档患者场景必然触发，空状态提示是必要的体验闭环。
2. 实现成本低。

**状态**：✅ 已确认
