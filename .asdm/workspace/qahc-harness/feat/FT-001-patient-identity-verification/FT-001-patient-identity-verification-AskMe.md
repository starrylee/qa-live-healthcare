# FT-001 患者身份验证与自动建档 — 需求访谈追问

> 本文档记录对 FT-001 患者身份验证与自动建档特性的逐问题追问，用于澄清需求模糊点后制定最终需求规格。

**创建日期**：2026-07-14
**负责人**：Ivy
**状态**：已完成

## 背景摘要

QA Healthcare 当前为微服务架构（qa-service-user :8080、qa-service-question :8081、qa-web :5173）。患者端问诊入口 `web/qa-web/src/views/Consultation.vue` 已在前端以本地 mock 实现"姓名+生日验证身份 → 自动建档 → 患者门户 → 切换用户"的完整交互，但后端 `qa-service-user` 仅有 `DoctorUserController`，尚无患者验证 API；架构文档规划的 `POST /api/patients/verify` 未落地。本特性将把该能力工程化：落地真实后端 API、规范业务键、对接持久化，并将前端从本地 store 改造为对接真实接口。

### 核心价值

- 患者**无需注册账号**即可凭"姓名+出生日期"完成身份识别，降低使用门槛。
- 首次验证自动建立健康档案并生成业务键，再次验证可复用同一档案并查看历史问诊。
- 支持"切换用户"（退出当前患者身份），满足多患者共用设备的场景。

### 变更范围

| 变更模块 | 变更内容 |
| ---------- | ---------- |
| qa-service-user（后端） | 新增患者实体（JPA）与 `POST /api/patients/verify` 接口；按姓名+生日匹配或新建档案并生成 `PAT-` 业务键；提供患者档案查询能力 |
| qa-service-question（后端） | 提供按患者查询问诊记录的 API（`GET /api/questions?patientId=`）以支持历史展示 |
| qa-web（前端） | `Consultation.vue` / `store` 从本地 mock 改为调用后端验证与历史接口；保留验证表单与切换用户交互 |
| 数据/部署 | 配套 MySQL 建表脚本（患者表）；复用 `docker-compose` 中 MySQL(:3307) |
| 总体计划 | 在"当前迭代特性"注册 FT-001（状态 🟣 澄清中） |

> 注：D3 决策选择"直接对接 MySQL+JPA，跳过内存阶段"，与项目文档定义的 Phase 1（内存 JSON）/ Phase 2（MySQL）演进路线不同。FT-001 因此成为首个落地真实 MySQL 的特性，需配套建表脚本与数据库连通。

### 初始需求

患者通过姓名+出生日期验证身份，首次验证自动建立健康档案，无需注册账号。患者在咨询页填写姓名和出生日期进行身份验证。系统匹配已有患者记录，若无则自动创建新档案（生成业务键）。验证成功后进入患者门户，可查看历史问诊记录。支持切换用户（退出当前患者身份）。

## 决策点

### 决策点 1：后端落地方式

**问题**：是否实现真实的患者验证 API，还是仅维持前端 mock？

**背景**：
- 前端 `Consultation.vue` + `store.verifyPatient` 已实现交互，但数据存于前端内存，刷新/多端不共享。
- 架构文档数据流已规划 `POST /api/patients/verify`（user 服务，生成 token）。

**选项**：

| 选项 | 描述 | 优点 | 缺点 |
| ------ | ------ | ------ | ------ |
| A | 后端实现真实 API（qa-service-user 新增 `POST /api/patients/verify`，生成业务键并维护患者档案） | 与架构规划一致；数据可持久共享；为后续认证/统计打基础 | 工作量更大，需配套持久化 |
| B | 仅前端 mock，维持现状 | 改动最小 | 数据不持久、不可跨端；与架构规划脱节 |

**推荐**：✅ 选项 A — 实现真实后端 API，与架构规划一致。

**确认理由**：
1. 验证/建档是核心业务，需持久化与跨端一致性。
2. 架构文档已将其纳入 user 服务职责范围。

**状态**：✅ 已确认

---

### 决策点 2：患者业务键生成规则

**问题**：患者业务键（patient id）采用何种生成规则？

**背景**：
- 当前前端使用 `patient${Date.now()}`（非语义化、并发下易碰撞、重启后不可复现）。
- 需求明确要求"生成业务键"。

**选项**：

| 选项 | 描述 | 优点 | 缺点 |
| ------ | ------ | ------ | ------ |
| A | `PAT-` + 时间戳/随机串（如 `PAT-20260714-8F3K`） | 语义化、可读、便于排查；基本唯一 | 非严格全局唯一（需配合唯一索引兜底） |
| B | UUID | 全局唯一、实现简单 | 无业务含义、可读性差 |
| C | 自增数字 | 简洁 | 需 DB 序列；Phase 1 内存态不支持（本特性已选 MySQL，技术上可行但语义弱） |

**推荐**：✅ 选项 A — `PAT-` + 时间戳/随机串语义化业务键。

**确认理由**：
1. 业务键需具备可读性与可排查性。
2. 配合数据库唯一约束可保证不重复。

**状态**：✅ 已确认

### 决策点 3：数据存储策略

**问题**：患者档案存放在哪里？

**背景**：
- 项目文档将 Phase 1 定义为内存 JSON 存储、Phase 2 为 MySQL+JPA。
- `docker-compose` 已具备 MySQL(:3307) 与 phpMyAdmin(:6080)。

**选项**：

| 选项 | 描述 | 优点 | 缺点 |
| ------ | ------ | ------ | ------ |
| A | Phase 1 先用内存存储（与现有 DoctorUser 一致），同时定义 JPA 实体便于 Phase 2 迁移 | 与既有 Phase 1 路线一致；改动小 | 数据重启丢失；与 D2 业务键持久化诉求有张力 |
| B | 直接对接 MySQL + JPA，跳过内存阶段 | 数据持久、贴合"建档"语义；一步到位 | 偏离文档 Phase 1 路线，成为首个真实 MySQL 特性，需建表脚本与 DB 连通 |

**推荐**：✅ 选项 B — 直接对接 MySQL + JPA（按用户决策，跳过内存阶段）。

**确认理由**：
1. 用户明确要求"直接对接 MySQL+JPA"，优先采纳。
2. "建档"语义要求数据持久，MySQL 更契合。
3. 注：此决策使 FT-001 成为首个落地真实 MySQL 的特性，需配套建表脚本并复用 `docker-compose` 的 MySQL 实例。

**状态**：✅ 已确认

### 决策点 4：安全与隐私边界

**问题**：姓名+生日属弱认证（知晓即可冒用），如何处理？

**背景**：
- 需求明确"无需注册账号"，即无密码。
- 任意知晓他人姓名+生日者均可冒用其身份查看/操作问诊记录。

**选项**：

| 选项 | 描述 | 优点 | 缺点 |
| ------ | ------ | ------ | ------ |
| A | 保持无密码弱认证，并在文档标注冒用风险、建议后续增强（手机号/短信） | 满足需求、风险可见 | 当前无防护 |
| B | 增加补充校验（手机号后四位/图形验证码） | 安全性提升 | 增加验证步骤，偏离"无需注册"的极简体验 |
| C | 保持现状，不做额外说明 | 最简 | 风险未记录，后续易遗漏 |

**推荐**：✅ 选项 C — 保持现状，不做额外说明（按用户决策）。

**确认理由**：
1. 用户明确选择保持现状且不做额外说明。
2. 记录于本文档以备后续审计追溯。

**状态**：✅ 已确认

### 决策点 5：身份匹配与去重规则

**问题**：姓名+出生日期如何匹配？同名同生日如何处置？

**背景**：
- 需保证"首次建档、再次登录命中同一档案"。
- 用户输入可能存在大小写、首尾空格、生日格式差异。

**选项**：

| 选项 | 描述 | 优点 | 缺点 |
| ------ | ------ | ------ | ------ |
| A | 姓名忽略大小写与首尾空格 + 生日按 `YYYY-MM-DD` 日期精确匹配；同名同生日视为同一患者 | 用户体验好、容错强 | 不同患者若同名同生日会被合并（弱认证固有风险，见 D4） |
| B | 严格区分大小写精确匹配 | 匹配精确 | 用户体验差（"张三"与"张三 "无法登录） |
| C | 姓名精确匹配 + 生日仅校验年月日（忽略时分秒） | 容错 | 与 B 类似，无实质增益 |

**推荐**：✅ 选项 A — 姓名归一化（去空格/小写）+ 生日日期精确匹配，同名同生日视为同一患者。

**确认理由**：
1. 提升验证成功率与体验。
2. 与"复用同一档案"的目标一致。

**状态**：✅ 已确认

---

### 决策点 6：历史问诊记录数据来源

**问题**：患者门户"历史问诊记录"数据如何获取？

**背景**：
- 患者门户需展示该患者的历史问诊。
- 问诊数据归属 `qa-service-question`。

**选项**：

| 选项 | 描述 | 优点 | 缺点 |
| ------ | ------ | ------ | ------ |
| A | 前端调用 question 服务 `GET /api/questions?patientId=` 获取 | 直连、职责清晰 | 需 question 服务具备按患者查询 API |
| B | 由 user 服务聚合（user 调用 question 后返回） | 前端只需调 user | 增加 user 服务耦合与转发开销 |
| C | 暂用前端本地 mock 数据 | 最简 | 与真实数据脱节 |

**推荐**：✅ 选项 A — 前端调用 question 服务按 `patientId` 查询。

**确认理由**：
1. 数据归属 question 服务，直连最自然。
2. 需确保 question 服务提供对应查询 API（纳入变更范围）。

**状态**：✅ 已确认

---

### 决策点 7：切换用户/退出语义

**问题**：退出（切换用户）后，已创建的患者档案是否保留？

**背景**：
- 需求要求"支持切换用户（退出当前患者身份）"。
- 需保证退出后再次以相同信息验证可复用档案与历史。

**选项**：

| 选项 | 描述 | 优点 | 缺点 |
| ------ | ------ | ------ | ------ |
| A | 退出仅清空当前登录态，档案持久保留，下次相同姓名+生日可重新登录并看到历史 | 符合"首次建档、再次登录" | 无 |
| B | 退出需二次确认弹窗，确认后才清除会话 | 防误触 | 增加一步交互 |

**推荐**：✅ 选项 A — 退出仅清登录态，档案持久保留。

**确认理由**：
1. 符合"首次创建、再次登录"的核心诉求。
2. 与 D3（MySQL 持久化）一致。

**状态**：✅ 已确认
