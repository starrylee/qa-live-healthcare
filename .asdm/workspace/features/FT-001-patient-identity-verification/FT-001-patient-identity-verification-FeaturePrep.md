## Feature 描述

QA Healthcare 当前为微服务架构（`qa-service-user` :8080、`qa-service-question` :8081、`qa-web` :5173）。患者端问诊入口 `web/qa-web/src/views/Consultation.vue` 已在前端以本地 mock 实现了"姓名+生日验证身份 → 自动建档 → 患者门户 → 切换用户"的完整交互，但后端 `qa-service-user` 尚无患者验证 API；架构规划的 `POST /api/patients/verify` 尚未落地。

本特性将该能力工程化：落地真实后端 API、规范业务键、对接 MySQL 持久化，并把前端从本地 store 改造为调用真实接口，使患者**无需注册账号**即可凭"姓名+出生日期"完成身份识别，首次验证自动建档、再次验证复用同一档案并查看历史问诊，并支持多患者共用设备的"切换用户"。

> 来源：关联 PRD 设计文档 `FT-001-patient-identity-verification-PRD.md`（来自 qahc-harness-toolset 的 design-overall / design-detail 产出）。

## 三要素分析

### 用户角色（Who）

| 角色 | 描述 | 与 Feature 的关系 |
| ------ | ------ | ------ |
| 患者（Patient） | 寻求医疗咨询的终端用户，无需注册账号、无密码 | 主要受益者与使用者：完成身份验证、自动建档、查看历史问诊、切换用户 |
| 共用设备的患者 | 同一设备上先后使用系统的多名患者 | 通过"切换用户"退出当前身份、复用持久化档案，避免互相串档 |

> 说明：本特性不直接涉及医生、管理员的操作界面；后端 API、数据库配置、代理/CORS 修复等属于工程交付依赖，对应内部（开发/运维）角色，但不作为本 Feature 拆分的用户故事主体视角。

### 功能意图（What）

**核心意图**：让患者无需注册即可凭"姓名+出生日期"完成身份识别，首次自动建立健康档案并生成业务键，再次验证复用同一档案。

**主要功能点**：
1. 患者验证建档 API（`POST /api/patients/verify`）：按姓名+生日命中复用 / 未命中新建建档，返回 `PAT-` 业务键与 `isNew` 标识。
2. 业务键生成：格式 `PAT-` + 日期 + 随机/纳秒串，全局唯一，作为患者档案主键。
3. 姓名归一化与去重：姓名 `trim`+`toLowerCase`、生日 `YYYY-MM-DD` 精确匹配、同名同生日视为同一患者；`(normalized_name, birthday)` 唯一索引防并发重复建档。
4. 患者档案查询（`GET /api/patients/{businessKey}`）：供门户展示与校验，不存在返回 404。
5. 历史问诊查询（`GET /api/questions?patientId=`）：由 `qa-service-question` 提供，按患者业务键返回问诊记录。
6. 前端改造：`Consultation.vue` / `store` 从本地 mock 改为异步调用 verify 与历史接口，并依据 `isNew` 区分「首次建档 / 欢迎回来」。
7. 切换用户：退出仅清前端登录态，后端档案持久保留，可再次验证命中历史。

**Feature 边界**：
- ✅ 包含：验证建档 API、业务键生成、姓名归一化与去重、档案查询、历史问诊查询、前端对接真实接口、切换用户语义。
- ❌ 不包含：医生账号/注册登录、密码认证或更强认证（决策 D4 保持弱认证现状）、统计分析能力、question 服务的完整业务（仅补齐数据源与查询所需最小范围）、问诊/回复业务本身的改造。

### 业务价值（Why）

**核心问题**：当前患者端问诊入口仅有前端 mock，后端无患者验证 API，真实建档与跨会话共享不可行；同一患者无法复用档案、无法查看历史问诊；多患者共用设备时无法安全切换。

**预期效果**：
- 降低使用门槛：患者无需注册即可问诊。
- 首次建档自动生成 `PAT-` 业务键，再次验证复用同一档案与历史。
- 支持多患者共用设备的"切换用户"，档案持久保留不串档。
- 为后续认证、统计、跨服务关联奠定一致的语义化业务键基础。

**成功指标**：
- 验证成功率：含大小写/首尾空格容错的姓名录入，可 100% 正确命中或新建建档。
- 复用率：已建档患者再次以相同信息验证，返回同一 `PAT-` 业务键。
- 历史问诊返回准确率：门户「我的问题」由后端历史接口正确渲染。
- 持久化：患者档案与问诊记录持久于 MySQL，服务重启不丢失。

## Feature 用户故事

```
作为一个 患者，
我想要 凭姓名+出生日期完成身份验证并自动建立健康档案，
以便 无需注册即可问诊，并在再次访问时复用同一档案、查看历史问诊。
```

## 假设与约束

### 假设

1. **技术假设**：`qa-service-user` 已具备 MySQL(:3307/healthcare) 数据源与 JPA 配置，可直接新增 `Patient` 实体并 `ddl-auto=update` 自动建表。
2. **技术假设**：前端 Vite / Nginx 代理可补充 `/api/patients`、`/api/questions` 路由，使 dev/prod 均可达对应后端（PRD §7 R1）。
3. **业务假设**：用户接受弱认证（仅姓名+生日），无需密码补充校验（PRD §1.4 决策 D4）。
4. **数据假设**：`qa-service-question` 可补齐 MySQL/JPA/CORS 配置，使 `patientId` 关联的问诊记录可查询（`patientId` 存储 user 服务生成的 `PAT-` 业务键）。
5. **业务假设**：同名同生日视为同一患者的去重策略，在当前业务场景下是可接受的。

### 约束

1. **技术约束**：必须直接对接 MySQL + JPA（决策 D3 跳过内存阶段），需保证数据库连通与建表/索引。
2. **合规约束**：弱认证存在身份冒用隐私风险，但按决策 D4 保持现状且不做额外说明，仅记录本文档备后续审计；建议后续特性补充更强认证。
3. **数据约束**：验证流程仅收集姓名+生日，不持久化 `phone` / `gender`（与弱认证目标一致）。
4. **兼容性约束**：业务键须与 `DoctorUser` 的字符串主键范式一致（字符串类型主键）。
5. **并发约束**：同名同生日并发建档不得产生重复档案/业务键（唯一索引 + 写入冲突回退查重）。
6. **一致性约束**：`CorsConfig` 与 `application.properties` 的凭证配置需统一（推荐 `true`），否则带凭证请求被拒（PRD §7 R4）。
