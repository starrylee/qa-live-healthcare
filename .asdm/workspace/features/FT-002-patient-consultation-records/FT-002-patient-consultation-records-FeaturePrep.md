## Feature 描述

患者通过 FT-001 身份验证进入患者门户后，需要一个清晰、有序的「我的问诊记录」视图：以列表形式查看自己提交的全部历史问诊，快速区分「待回答 / 已回答」，并对已回答的问题展开查看医生回复与回复时间。该特性聚焦于**前端展示层**，复用 FT-001 提供的历史问诊查询接口与数据模型，不改变后端领域逻辑。

> 来源：关联 PRD 设计文档 `FT-002-patient-consultation-records-PRD.md`（来自 qahc-harness-toolset 的 design-overall / design-detail 产出，PRD v1.1.0）。

## 三要素分析

### 用户角色（Who）

| 角色 | 描述 | 与 Feature 的关系 |
| ------ | ------ | ------ |
| 已验证患者（普通患者） | 已通过 FT-001 身份验证并进入患者门户的终端用户 | 主要受益者与使用者：查看本人全部问诊记录、区分状态、展开查看答案 |
| 首次建档患者 | 通过 FT-001 首次建档、尚无任何问诊记录的患者 | 触发空状态场景，验证体验闭环的完整性 |

> 说明：本特性为纯前端展示层，不直接涉及医生、管理员的操作；后端 `qa-service-question` / `qa-service-user` 仅作为数据来源（复用 FT-001 接口），不作为本 Feature 拆分的用户故事主体视角。

### 功能意图（What）

**核心意图**：让已验证患者以清晰有序的「我的问诊记录」视图查看本人全部历史问诊，快速区分「待回答 / 已回答」，并对已回答记录展开查看医生回复与回复时间。

**主要功能点**：
1. 倒序列表展示本人全部问诊记录（按提交时间倒序，每条展示咨询医生姓名、状态标签、问题内容摘要、提交时间）。
2. 状态标签区分「待回答 / 已回答」（复用 `a-tag`，文案走 i18n）。
3. 内容摘要（截断约 50 字 + 省略号）与内联手风琴展开（完整问题 + 医生回复 + 回复时间）。
4. 状态筛选标签页（全部 / 待回答 / 已回答），纯前端按 `status` 过滤。
5. 客户端分页「加载更多」（前端对已加载全量数据切片，首屏 N 条 + 追加）。
6. 空状态提示「暂无问诊记录」（复用 `a-empty`，文案走 i18n）。
7. 数据来源接口化（`GET /api/questions?patientId=`）与门户文案国际化（`consultation.*` 命名空间，支持中英切换）。

**Feature 边界**：
- ✅ 包含：患者门户内的问诊记录列表组件（倒序列表、状态标签、内容摘要、内联手风琴展开、状态筛选标签页、空状态、客户端分页「加载更多」）；前端取数从 mock 切换为真实接口、文案 i18n 迁移。
- ❌ 不包含：后端领域逻辑与接口新增（`qa-service-question` 无变更，复用 FT-001 规划的 `GET /api/questions?patientId=`）；医生端能力；「已关闭（closed）」状态；后端分页（仅预留可选参数）；问诊/回复业务本身的改造。

### 业务价值（Why）

**核心问题**：患者进入门户后缺乏有序的本人历史问诊视图，难以区分「待回答 / 已回答」，已回答的医生回复无处查看；长列表查找成本高、体验差；首次建档患者面对空白列表易产生困惑。

**预期效果**：
- 以清晰倒序列表呈现本人全部问诊，状态一目了然。
- 已回答记录可内联展开查看医生回复与回复时间，形成完整上下文。
- 状态筛选、内容摘要折叠、客户端分页与空状态共同保障任意数据规模下的可读性与体验闭环。

**成功指标**：
- 倒序正确性：本人全部问诊按提交时间倒序渲染。
- 状态区分度：待回答 / 已回答以标签清晰区分。
- 展开完整度：已回答项可查看完整问题、医生回复与回复时间。
- 筛选即时性：状态筛选纯前端即时过滤，无需重新请求。
- 加载平滑性：首屏轻量，加载更多平滑追加。
- 空状态友好度：无记录时显示「暂无问诊记录」，不出现空白困惑。

## Feature 用户故事

```
作为一个 已通过 FT-001 身份验证的患者，
我想要 以清晰有序的列表查看本人全部历史问诊记录，并区分待回答/已回答、展开查看答案，
以便 快速掌握自己的问诊进展与医生回复，获得完整的门户体验。
```

## 假设与约束

### 假设

1. **技术假设**：FT-001 规划的 `GET /api/questions?patientId=` 接口（由 `qa-service-question` 提供）最终会实现并可访问（PRD §5.3 待确认项）。
2. **技术假设**：前端 `store.state.currentPatient.id` 即 `patientId`，且其类型与后端 FT-001 规划一致（PRD §7 R3），避免过滤失效。
3. **业务假设**：本期仅需「待回答 / 已回答」两种状态，「已关闭（closed）」不在本期展示范围（PRD §1.4 决策 D3）。
4. **数据假设**：接口返回的 `doctorName` 已由 `qa-service-question` 聚合 `t_user.real_name` 提供，前端不直连 `qa-service-user`（PRD §6）。
5. **技术假设**：接口优先按 `submitTime` 倒序返回；若顺序不确定，前端以 `dayjs(submitTime).valueOf()` 降序兜底排序，需与后端约定时间时区基准（PRD §7 R4）。
6. **技术假设**：FT-001 接口就绪前，沿用现有 `data/question-list.json` mock + `store.getQuestionsByPatient` 作为并行开发兜底（PRD §3.1 R1）。

### 约束

1. **技术约束**：必须复用 FT-001 接口，不新增后端接口与领域逻辑，不侵入 FT-001 已规划的接口契约（PRD §1.3、§1.4 决策 D1）。
2. **技术约束**：仅前端展示层，依赖 Ant Design Vue 组件（`a-tag` / `a-collapse` / `a-tabs` / `a-empty`）、vue-i18n 与 dayjs，并复用现有门户结构与交互（PRD §3.2）。
3. **兼容性约束**：未回答项的 `answer` / `answerTime` 为 `null` 时必须正常渲染（PRD §8.3.2，依赖接口契约保障）。
4. **兼容性约束**：中英文混排「约 50 字」截断按字符数 `slice(0,50)` + 省略号，不按字节（PRD §7 R6）。
5. **范围约束**：状态枚举仅取 `pending` / `answered`，不在前端展示 `closed`（PRD §5.2）。
6. **一致性约束**：前后端需锁定 §5 字段映射契约（如 `question`↔`content`、`submitTime`↔`created_at`、`answerTime`↔`Answer.created_at`），DTO 层统一转换（PRD §7 R2）。
